# Bob Go Channel Integration — Functional Specification

Platform-agnostic functional spec for a Bob Go shipping channel integration. This document describes **what** an integration must do, written in generic e-commerce terms. Implementation reference: the WooCommerce plugin in this repository.

Use this as the starting context for building Bob Go integrations on other platforms (Magento, Shopify, custom carts, etc.).

---

## 1. Overview

The integration plugs a merchant's e-commerce store into Bob Go so that:

1. Shoppers see live, accurate shipping rates at checkout (Rates at Checkout / RAC).
2. Orders flow automatically from the store to Bob Go for fulfilment.
3. Fulfilment, tracking, and status updates flow back from Bob Go to the store (via webhooks, with a reconciliation safety net).
4. Shoppers and merchants can view shipment tracking inside the store.
5. Merchants can configure all of the above from a single settings area.

Each store is identified to Bob Go as a **channel**. A channel is created by Bob Go and is bound to the store's canonical URL.

---

## 2. Authentication & API Connection

### 2.1 Credentials

The integration must store two secrets, both encrypted at rest using a platform-native key:

| Credential | Purpose |
|---|---|
| **API key** | Bearer token for all outbound calls to Bob Go |
| **Webhook secret** | HMAC signing key for verifying inbound webhooks. **Merchant-issued** — never auto-generated by the integration. |

Both are entered by the merchant in the settings UI and persisted encrypted.

### 2.2 Environment

The integration supports multiple environments (production, staging, sandbox/dev). The merchant selects the environment; the base URL is derived from it. Production is the default.

### 2.3 Required headers on every outbound request

```
Authorization: Bearer {api_key}
Content-Type: application/json
Accept: application/json
bobgo-channel-identifier: {canonical_store_url}
```

The channel identifier is the store's canonical URL and must be stable across the integration's lifetime — it is how Bob Go associates inbound calls with the right channel.

### 2.4 Test connection

A "Test connection" action on the settings page must call `GET /v2/webhooks` and surface a clear result:

- **200** → connected.
- **401** → invalid API key.
- **404** → API key valid but channel not enrolled (merchant must finish setup on Bob Go side).
- Network / timeout → surfaced with a generic "couldn't reach Bob Go" message.

### 2.5 Defaults

- Request timeout: 30s (configurable, 5–60s).
- SSL verification: on (toggleable for debugging).

## 3. Rates at Checkout (RAC)

### 3.1 Endpoint

`POST /v2/rates-at-checkout`

### 3.2 Request payload

```jsonc
{
  "collection_address": {            // origin / merchant address
    "company": "...",
    "street_address": "...",
    "local_area": "...",             // suburb
    "city": "...",
    "zone": "...",                   // province / state
    "code": "...",                   // postal code
    "country": "ZA"
  },
  "delivery_address": { /* same shape, from shopper checkout */ },
  "items": [
    {
      "description": "...",
      "price": 0,                    // unit price
      "quantity": 1,
      "length_cm": 0,
      "width_cm": 0,
      "height_cm": 0,
      "weight_kg": 0
    }
  ],
  "declared_value": 0,               // sum of (unit_price * quantity)
  "handling_time": 0
}
```

### 3.3 Response & display

Bob Go returns an array of rate options. Each must be rendered as a selectable shipping method at checkout:

| Field | Display |
|---|---|
| `service_name` | Method label |
| `service_code` | Internal — store on the order line so Bob Go knows which service the shopper picked |
| `total_price` | Method price |
| `description` (optional) | Sub-text under the label, behind a setting |
| `min_delivery_date` / `max_delivery_date` (optional) | "Arrives X–Y" timeframe, behind a setting |

### 3.4 Caching

Two-tier caching is required because a single checkout often triggers multiple rate lookups:

1. **In-request memoisation** — keyed by request hash; prevents duplicate calls within one checkout calculation.
2. **Short-lived persistent cache** — 15 minutes default (configurable), keyed by request hash.
3. **Negative cache** — when Bob Go returns no rates or errors, cache the empty result for ~30s to absorb retries without hammering the API.

### 3.5 Limits & safety

- Cap displayed rates at 20 (configurable). Log overflow.
- If the API fails or returns no rates, the integration must fail soft: log the event, show no Bob Go rates, and let the platform fall back to whatever other shipping methods are configured.

### 3.6 Origin address resolution

The merchant can choose whether the origin is:

- The platform's configured store address, or
- A dedicated "Site address" defined inside Bob Go settings.

This toggle lives in the settings UI.

### 3.7 Suburb / local area field

Many regions (South Africa especially) require a suburb separate from city for accurate rating. The integration must:

- Add a **suburb** field to the checkout address form (both classic and any block-based / headless checkout the platform supports).
- Persist it to the order's shipping address.
- Send it as `delivery_address.local_area` in the RAC payload and in order sync.
- Allow the merchant to customise the field label and help text.

## 4. Order Sync (Outbound)

### 4.1 When to sync

Orders should sync to Bob Go on:

| Trigger | Behaviour |
|---|---|
| Order created | Schedule a sync. If the order is unpaid / pending, delay ~60s and re-check up to ~60 times (≈ 1 hour) waiting for payment confirmation before sending. |
| Order updated (address, items, etc.) | Sync only if the order has materially changed (see dirty check). |
| Order status changed | Sync the new status to Bob Go. |

Syncs run **asynchronously** via the platform's job/queue system — never inline with checkout or admin actions.

### 4.2 Syncable statuses

Orders in these statuses are eligible for sync:
`processing`, `on-hold`, `completed`, `shipped`, `partially-shipped`.

Cancellations are sync'd as a status change.

### 4.3 Endpoints

| Action | Endpoint |
|---|---|
| Create | `POST /v2/orders` → response includes Bob Go order id |
| Update (address, items, value) | `PATCH /v2/orders/{id}` |
| Status change | `PATCH /v2/orders/{id}/status` |

### 4.4 Payload

```jsonc
{
  "order_number": "...",             // human-readable store order number
  "channel_ref_id": "...",           // store's internal immutable order id (idempotency key)
  "customer": { "name": "...", "email": "...", "phone": "..." },
  "billing_address":  { /* see address shape in §3.2 */ },
  "shipping_address": { /* see address shape in §3.2 */ },
  "items": [
    {
      "order_item_id": "...",        // store's line item id
      "description": "...",
      "quantity": 1,
      "unit_price": 0,
      "sku": "...",
      "weight_kg": 0,
      "length_cm": 0,
      "width_cm": 0,
      "height_cm": 0
    }
  ],
  "declared_value": 0,
  "service_code": "...",             // from the rate the shopper picked at checkout
  "custom_fields": { /* merchant-configured meta mapping, see §9 */ }
}
```

### 4.5 Idempotency & dirty checking

- **`channel_ref_id`** is the immutable store order id and is Bob Go's idempotency key. The same value on a `POST /v2/orders` must never create a duplicate.
- The integration computes a **sync hash** (e.g. MD5) over the order's syncable state and stores it on the order. An update only triggers a sync if the hash has changed.
- The job queue must reject duplicate scheduled syncs for the same order.

### 4.6 Result tracking

Per order, persist:

- Bob Go order id (numeric) and order ref (string, immutable, used for webhook lookups).
- Last sync status (`pending` / `success` / `failed`).
- Last sync timestamp.
- Sync hash.
- A manual "Resync" action must be available on the order detail page.

## 5. Webhook Handling (Inbound)

### 5.1 Endpoint

The integration exposes one webhook endpoint, e.g. `POST /bobgo/v1/webhook`.

### 5.2 Authentication

- Bob Go signs each request with `HMAC-SHA256(raw_body, webhook_secret)`, base64-encoded.
- The signature arrives in the `Bobgo-Webhook-Signature` header.
- The integration must compute the same digest and compare in **constant time**.
- If the secret is not configured, or the signature mismatches, **return 403 immediately**. Never process the body.

### 5.3 Topics

| Topic | Trigger action |
|---|---|
| `fulfillment/created` | Fetch full fulfilment state from Bob Go (§5.5) and persist to the order. |
| `tracking/updated` | Same fetch-and-persist as `fulfillment/created` (the webhook is a thin trigger). |
| `order/updated` | Update the order's delivery address and metadata in the store. Set a short-lived **loop guard** so the resulting store-side update doesn't immediately echo back to Bob Go. |

### 5.4 Idempotency

Each webhook carries an `event_id`. The integration must deduplicate on this id (the sync log table is the natural place) so retries don't reprocess.

### 5.5 Fulfilment refresh (`GET /v2/order-fulfillments?order_id={id}`)

Returns one or more shipments per order. For each shipment, persist:

- `shipment_id`, `courier`, `service_level`
- `tracking_number`, `tracking_url`
- `status`, `submission_status`
- `parcels[]`
- `tracking_events[]` (timestamp, status, message, location)
- `items[]` — Bob Go's item references, mapped back to store line items via, in order of preference: `channel_ref_id` → stored Bob Go item id meta → name match.
- `estimated_delivery`, `fulfilled_at`

Store the full shipments array on the order (e.g. as a JSON-encoded meta field).

### 5.6 Fulfilment-derived order status

From the shipments, derive a fulfilment status:

- All items shipped → **shipped**
- Some items shipped → **partially-shipped**
- Otherwise → no change

If the merchant has opted into custom statuses (§9), apply them to the order. Otherwise leave the order status alone and only update the shipment metadata.

### 5.7 HTTP responses

| Outcome | Status |
|---|---|
| Processed successfully | 200 (or 202 if processing is deferred) |
| Signature invalid / missing | 403 |
| Missing/unknown topic, malformed body | 400 |
| Order not found locally | 200 — acknowledge, but record in the sync log |

Always log the actual HTTP status returned (this matters for debugging delivery issues).

## 6. Reconciliation (Safety Net)

A scheduled job runs hourly to catch missed webhooks (network drops, downtime, etc.).

### 6.1 Scope

All orders in active fulfilment statuses: `processing`, `on-hold`, `shipped`, `partially-shipped`.

### 6.2 Behaviour

For each in-scope order:

1. Call `GET /v2/order-fulfillments?order_id={bob_go_id}`.
2. Full-replace the shipments meta on the order (Bob Go is the source of truth).
3. Re-derive fulfilment status as in §5.6.
4. **Only change the order status if it actually needs to change.** Reconciliation must not force a write on every run.

### 6.3 Batching

Process in batches (e.g. 100 orders per scheduled batch) to avoid memory / timeout issues on large stores.

### 6.4 Manual trigger

Provide a "Run reconciliation now" button in the admin UI for support purposes.

---

## 7. Tracking (Shopper-Facing)

### 7.1 What to render

From the shipments meta on an order, render per shipment:

- Tracking number, linked to `https://track.bobgo.co.za/{tracking_number}` (use the corresponding sandbox/dev host if the integration is in a non-production environment).
- Courier and service level.
- Latest status / status badge.
- Estimated delivery date if present.
- A timeline of tracking events (timestamp, message, location).

### 7.2 How to expose it

The integration should expose the tracking widget through whatever surface the platform offers — shortcodes, blocks, page widgets, and/or theme partials. Magento equivalent would be a CMS widget plus a block class that can be embedded in PHTML / a CMS block.

The merchant configures **one tracking page** in settings (a CMS page they own). Order confirmation emails and order detail pages link to this page; the page renders the widget and looks up the order by either order number + email or a signed tracking token in the URL.

## 8. Order Metadata

The integration must persist the following per order (names are illustrative):

| Key | Purpose |
|---|---|
| `bobgo_order_id` | Numeric Bob Go id (from create response or webhook). |
| `bobgo_order_ref` | String reference returned by Bob Go, used for webhook lookups. Immutable. |
| `bobgo_sync_status` | `pending` / `success` / `failed`. |
| `bobgo_sync_hash` | Last-synced state hash for dirty checking. |
| `bobgo_last_synced` | ISO timestamp. |
| `bobgo_last_webhook` | ISO timestamp of last inbound webhook. |
| `bobgo_shipments` | JSON array of shipment objects (see §5.5). |

Per line item:

| Key | Purpose |
|---|---|
| `bobgo_item_id` | Bob Go's internal line item id, used to map fulfilment items back to the store. |

## 9. Admin UI

### 9.1 Settings, tabbed

| Tab | Contents |
|---|---|
| **Overview** | Connection status, plugin version, quick links. |
| **Connection** | API key, webhook secret, environment selector, **Test connection** button. |
| **Rates at Checkout** | Enable/disable, hide other carriers toggle, test RAC button, show description toggle, show delivery timeframe toggle, origin address toggle (store address vs Bob Go Site Address). |
| **Tracking** | Tracking page selector, embed snippet help. |
| **Checkout fields** | Suburb field label / help text. Custom field mapping table (up to 10 rows): store meta key → Bob Go field name. |
| **Notifications** | Email mode: platform sends emails (default) vs Bob Go sends emails. When set to Bob Go, suppress the platform's shipped/completed notification. |
| **Advanced** | Custom fulfilment status toggle (`shipped` / `partially-shipped`), reconciliation controls, sync log viewer, "Run reconciliation now". |

### 9.2 Order list

Add a "Bob Go" column to the order list showing:

- Sync status badge (`pending` / `success` / `failed`), or
- Shipment count + latest tracking status if shipped.

Link through to Bob Go's dashboard for the order.

### 9.3 Order detail

A panel on the order page showing:

- Bob Go order ref (linked to Bob Go dashboard).
- Sync status, last synced, last webhook received.
- One card per shipment: tracking number, courier, status, parcels, tracking events timeline, estimated delivery.
- **Resync** button (manual retry, especially for failed syncs).

## 10. Sync Log

A dedicated table (e.g. `bobgo_sync_log`) for audit and debugging.

### 10.1 Columns

`order_id`, `event_type`, `direction` (inbound/outbound), `payload` (JSON), `http_status`, `success` (bool), `event_id` (for dedupe + correlation), `retry_count`, `created_at`.

### 10.2 Event types

`webhook_received`, `webhook_rejected`, `fulfillment_received`, `tracking_updated`, `order_updated_inbound`, `order_created`, `order_updated_outbound`, `order_status_changed`.

### 10.3 Retention

Default 30 days, purged daily by a scheduled job. Setting is configurable.

### 10.4 Viewer

Filterable in the admin UI by order, event type, success/failure, date range.

---

## 11. Email Control

The merchant chooses who sends fulfilment / shipped notifications:

| Mode | Effect |
|---|---|
| **Platform** (default) | Platform sends its standard "your order has shipped" email. |
| **Bob Go** | Suppress the platform's shipped notification. Order confirmation (purchase receipt) is still sent by the platform. |

Implementation in Magento terms: an observer / plugin that conditionally cancels the email transport for the shipped notification when mode = Bob Go.

---

## 12. Custom Field Mapping

Merchants can map up to 10 store-side order meta keys to Bob Go custom fields. These are included on the outbound order payload under `custom_fields`. Used for things like gift-message text, internal warehouse refs, B2B PO numbers.

## 13. Installation, Upgrade & Multisite

### 13.1 On install

1. Create the sync log table.
2. Register custom fulfilment statuses (`shipped`, `partially-shipped`) if the feature is opted in.
3. Schedule recurring jobs: hourly reconciliation, daily sync log purge.
4. Migrate config from any predecessor integration if detected (for the Woo plugin this was the legacy uAfrica option set — Magento likely won't need this).

### 13.2 On uninstall / deactivate

- Unschedule all recurring jobs.
- Keep order metadata so shipment history isn't lost.
- Sync log: keep on deactivate, prompt on full uninstall.

### 13.3 Multisite / multi-store

The integration must support a configuration **per store / per channel**. Each store has its own API key, webhook secret, and channel identifier.

---

## 14. Required Background Jobs

| Job | Frequency | Purpose |
|---|---|---|
| Order sync | On-demand | Push order creates / updates / status changes to Bob Go. |
| Pending-order poll | Per pending order, ~60s × up to 60 attempts | Wait for payment confirmation before initial sync. |
| Reconciliation | Hourly, batched | Refresh fulfilment state for active orders (§6). |
| Sync log purge | Daily | Delete entries older than retention window. |

All jobs must be **idempotent** and **restart-safe**.

---

## 15. Error Handling Principles

- **Fail soft at checkout.** If Bob Go is unreachable, show no Bob Go rates and let other shipping methods carry the checkout.
- **Never swallow errors silently.** Every failure is recorded in the sync log with HTTP status and payload.
- **Never log secrets.** API keys, webhook secrets, full Authorization headers must be redacted in logs.
- **Validate all inbound boundaries.** Webhook signature is the first check. Payload shape is the second.
- **Constant-time comparisons** for signatures.
- **Loop guards** on inbound address updates so a webhook update doesn't immediately bounce back out as an outbound sync.

---

## 16. Non-Goals

The following are explicitly **not** the integration's responsibility:

- Generating waybills / labels — handled inside Bob Go.
- Carrier selection logic — Bob Go returns rates, the shopper picks.
- Returns / RMA flows — out of scope for v1.
- Payments — fully owned by the platform.

## Appendix A — Endpoint Summary

| Direction | Method | Path | Purpose |
|---|---|---|---|
| → Bob Go | GET | `/v2/webhooks` | Test connection / verify channel enrolment. |
| → Bob Go | POST | `/v2/rates-at-checkout` | Live rates at checkout. |
| → Bob Go | POST | `/v2/orders` | Create order. |
| → Bob Go | PATCH | `/v2/orders/{id}` | Update order. |
| → Bob Go | PATCH | `/v2/orders/{id}/status` | Update order status. |
| → Bob Go | GET | `/v2/order-fulfillments?order_id={id}` | Fetch authoritative fulfilment state. |
| ← Bob Go | POST | `{store}/bobgo/v1/webhook` | Inbound webhook (`fulfillment/created`, `tracking/updated`, `order/updated`). |

```
company, street_address, local_area, city, zone, code, country
```

Used identically for `collection_address`, `delivery_address`, `billing_address`, and `shipping_address`.
